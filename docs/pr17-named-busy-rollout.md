# PR #17 名前付き予定時間の段階的公開

PR #17はDraftのままにする。0011は意図的に未適用。0019と0020は本番適用済みであり、再適用しない。0020の追加は通知確認テーブルだけで、既存の予定・設定行を変更しない。

## 公開前の互換性

- 0020対応Backendを先行公開しても、告知未確認の利用者には0019の旧設定が引き続き適用される。旧OFFなら名前は返さず、旧ONなら従来どおり名前を返す。
- 新Frontendは上部に指定文言を表示し、本人が「内容を確認しました」を押した時だけサーバーに確認日時を記録する。これは公開可否の同意チェックではない。新仕様を知る前に既存のOFFを上書きしない。
- 確認後は有効な同一グループ所属者に表示名と予定時間帯を返す。旧設定値はこの利用者の表示判定に使わない。旧設定APIのGETはONと新方針を返し、旧FrontendからのOFF要求は409で拒否する。
- 既存のService Workerにはfetchハンドラーがない。古いページや複数端末は残り得るため、旧Frontend用APIは維持する。既に開いている古い画面が自動更新される保証はない。別端末で確認した場合、古い画面のチェック表示は再取得まで古い可能性があるが、OFF送信を成功扱いにはしない。
- 告知を見ていない既存利用者は匿名のまま。アプリ内バナーの表示だけを全員への通知完了と数えない。確認済み件数は0020テーブルから集計できる。実際のPush送信はこのPRに含めない。

## 公開判定の証拠と残余リスク

- **本番で確認済み（2026-10-31時点の読み取り集計）**: 有効利用者5人・有効所属12件。旧設定ONは0人・0所属、旧OFF相当は5人・12所属（明示的OFFは1人・1所属）、告知確認済みは0人。旧OFF相当には設定行がない既定OFFも含む。集計は個人識別子を返さず、本番D1を書き換えていない。現行WorkerのCron、Logs、D1 journal、GitHub CIは別途確認済み。
- **合成データとコードで確認済み**: Backendテストでは告知未確認の旧OFFは名前なし、旧ONは名前あり、確認後は有効な同一グループ内で名前と時間帯を表示し旧OFF要求を409で拒否する。別グループの予定は匿名で、タイトル・メモ・勤務先・給与などは共有応答に含めず、退出・未所属のアクセスを拒否する。Frontendテストでは同意チェック撤去と名前を私的な予定欄から推測しない表示を確認した。告知バナーと確認ボタンの処理はコードで確認したが、実ブラウザでの操作は未検証。
- **本番で対象外（N/A）**: 旧設定ON利用者の現行Workerに対する実応答。対象者が0人なので本番でON状態を作って検証しない。マージ判断の直前にONの集計が増えていたらN/Aを取り消し、安全な読み取り検証または別途の明示的なリスク受容を要する。
- **本番で未検証**: 既存の旧OFF利用者の認証済みAPI応答、古いタブ・複数端末での表示、iPhone Safari/PWA実機、新Frontend公開後の告知表示。旧OFFの実応答に想定外の名前が含まれる場合は現在の有効利用者最大5人・所属12件にプライバシー影響が及び得る。これはテスト成功を本番成功へ読み替えられない残余リスク。

### 改訂したマージ準備ゲート

1. PR HEADの差分とFrontend・Backend・Securityテスト、型チェック、Worker dry-run、必須CIが成功し、上記の旧ON・旧OFF・告知後・グループ外・詳細非公開の合成データ証拠を維持する。
2. 現行Worker・D1・Cron・Logsの監査で新たな異常がなく、旧ONが0人であることをマージ判断時の読み取り集計で確認する。0人なら旧ONの本番実応答ゲートをN/Aとする。
3. 旧OFFの本番認証済み応答は未検証のまま記録し、公開判断者が上記の影響範囲と古い端末のリスクを**明示的に受容した場合に限り**、本番実応答を必須とするゲートに代えて合成データ・コード・監視の証拠を採用する。受容がなければNO-GO。未検証を成功済みと記録しない。
4. マージは別途承認後に行う。Vercel Production公開後は告知確認前の匿名表示、確認後の名前表示、APIエラーと古い端末の報告を監視し、異常があれば追加の公開作業を止める。

## 公開手順と停止条件

1. PRのhead・必須チェック・Draft状態、現行Worker version、D1 ID、journalを照合する。0011未適用、0019・0020適用済み、journal 20件を再確認する。0020は再適用しない。
2. 取得済みの暗号化SQLバックアップ、SHA-256、隔離復元、外部キー確認、Time Travel bookmarkの記録を照合する。不要な再取得や本番データ変更はしない。
3. 公開済みの0020対応Workerについて、DashboardのCron Events、scheduled outcome、Workers Logs、D1・通知関連エラーを監査する。旧設定GET/POSTと旧OFF利用者の匿名表示は合成データのテストで確認し、本番では未認証GETや静的配信など書き込みのない確認だけを行う。マージ準備は上記の改訂ゲートで判定する。
4. `backend/wrangler.production-0020.review.jsonc` は0020単独適用時の記録として保持する。Worker deployには使用しない。Workerの再デプロイ、D1本番データの変更、通知確認の代理操作はしない。
5. 別途承認後、PRを通常マージしVercel ProductionのREADY・merge SHA・正式ドメイン・Production Verifyを確認する。新Frontendのバナー表示と確認操作を合成データおよび安全な実運用範囲で確認する。
6. 確認済み本人だけ名前表示に切り替わること、他グループ匿名、未認証・退出済み拒否、詳細非公開を検証する。古いService Worker/タブ、複数端末、告知未確認者の匿名表示を監視する。

異常時はマージを停止する。0020後に0019以前のWorkerへ戻さない。復旧には0020対応コードで名前付けを止めるWorkerを用意し、別途承認を得る。DB全体の自動巻き戻しはしない。Frontend障害はBackendを維持し、直前の正常なFrontendへの復旧を検討する。ただし旧画面のチェック状態とサーバー状態が食い違う端末については再読み込みの案内が必要。
