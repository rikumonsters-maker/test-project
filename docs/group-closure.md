# 最後のメンバーによるグループ終了（ローカル実装）

## 動作

グループ管理の「グループから退出」は、認証済みの `/api/groups/leave/options` で現在の人数を確認する。本人が最後の有効なアカウントメンバーならグループ名を含む確認ダイアログを開き、「はい」で `/api/groups/delete` に `groupId` だけ送る。2人以上なら従来の退出、募集・日程調整の終了または引き継ぎを使う。

削除APIは本人の現行所属と有効メンバー数1人を再確認する。D1 batch内でも同じ条件を再確認し、グループの `closed_at`、終了者のID、管理版数を記録する。有効メンバー行は削除せず、`left_at` と `departed_user_id` を記録して `user_id` と旧アクセストークンを失効させる。グループ通知履歴は失効し、未送信のグループPushキューは削除する。最後の整合性アサーションが失敗すればbatch全体がロールバックされる。同一ユーザーの再試行には成功済みを返す。

共有予定、募集、仮予定、投票、日程調整、共有リマインダー、メンバー履歴は保持する。進行中の日程調整も履歴のまま残し、API・Cron・通知の対象から外す。個人予定、家計簿、シフトの元データは変更しない。

## DBとアクセス制御

`0018_group_closure.sql` は0017の後に適用する。既存の0014a〜0017は変更しない。`active_group_members` は `groups.closed_at IS NULL` のグループだけ返すため、所属を必須とする既存のグループAPI、共有カレンダー、招待、予定、投票、通知の認可を共通で遮断できる。終了後に遅れて届く古いWorkerの書き込みは、メンバー再有効化と共有予定・募集・日程調整・投票等の変更をDBトリガーで拒否する。0014aの削除保護と0015の履歴保護は維持する。

## 検証と公開時の注意

VitestのローカルD1で0018まで順に適用し、失敗時のbatchロールバック、参加との競合、再試行、招待・API遮断、履歴保持、外部キーとトリガーを検証する。Frontendでは確認ダイアログの「いいえ」、二重送信防止、人数変更を検証する。

本番反映は別工程。0016・0017が本番未適用なので、本番journalとD1 IDを直前確認し、0011を巻き込まない専用migration設定で0016→0017→0018を段階適用する。各段階でスキーマ、件数、外部キーを確認し、対応WorkerとFrontendの切替を計画する。0018適用後は0018非対応のWorkerへ戻さない。

外部Pushサービスへ既に送信を開始したリクエストをDBだけで取り消すことはできない。終了処理はキューを削除し、送信直前にも所属とキュー行を再確認するが、その照会と外部送信の間の競合は残る。本番の厳密な送信停止保証が必要なら、外部送信と終了操作を直列化する仕組みを別途設計する。
