# 共通空き時間検索 Phase 1

## 仕様

- グループのアカウント登録済み現役メンバーを2〜20人選択する。検索者も現役メンバーでなければならない。
- 開始日から終了日まで最大14日。必要時間は60〜360分、30分刻み。毎日9:00〜22:00に30分刻みで開始できる候補を返す。
- `POST /api/shared/availability/search` の本文は `{groupId,userIds,startDate,endDate,durationMinutes}`。応答は日別の `slots` と `unconfirmedUserIds`。このAPIは読み取り専用。
- 既存の `POST /api/shared/availability` は従来の本文と応答を維持し、時間帯の取得・夜勤処理を新APIと共通化する。
- 共有予定、個人同期予定、旧式個人予定、シフトを時刻だけで照合する。日付をまたぐシフトは両日に反映する。
- 検索結果は登録済み予定から計算した「候補」であり、本人の最新状態の保証ではない。

## 未確認の扱い

`0016_common_availability_coverage.sql` は、空の月を含むシフト全件同期の完了月を、グループと**メンバーID**単位で記録する。個人予定の同期開始が未確認、または検索日・前日の月のシフト同期記録がないメンバーを `unconfirmedUserIds` に入れる。前日の月も調べるのは、月末の夜勤が翌月1日の朝に及ぶため。退出後に再参加するとメンバーIDが変わるため、過去の確認状態は引き継がない。UIは未確認者がいる候補を「要確認」と表示する。

既存の同期記録は復元できないため、migration直後は全メンバーのシフト月が未確認になる。本人の端末からその月の全件同期が成功すると記録される。

## プライバシーと互換性

検索SQLは時刻・日付・対象者IDだけを読み、個人予定のタイトル・メモ、シフトの勤務先・給与を取得しない。要求されたユーザーIDは全件現役グループメンバーであることを確認し、検索中にメンバー構成が変わった場合は409でやり直しを求める。

今回の変更は検索UI・APIと同期完了記録のみ。募集、投票、日程確定、通知、退出の処理は変更しない。0016は新規テーブル・トリガー・索引のみで、既存データを削除しない。

## ローカル確認と将来の公開

CloudflareテストD1でmigration 0001〜0016を適用し、14日制限、権限、夜勤、予定の交差、機密情報の除外、空のシフト月、退出・再参加を検証する。Frontendテスト、Worker型チェック、dry-runも実行する。

本番公開には0016をWorkerより先に適用する必要がある。本番で未適用の別migrationがある場合は、全件適用コマンドを使わず、0016専用の設定と適用対象を別途レビューする。今回、本番環境への適用はしない。
