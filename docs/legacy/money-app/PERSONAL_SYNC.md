## DB / API

`0012_personal_event_sync.sql` は追加のみ。既存テーブルやデータを削除・初期化しない。

| テーブル | 用途 |
| --- | --- |
| personal_events | (user_id,id)で所有者分離。日付、開始/終了時刻、終日、タイトル、メモ、extra_json、version、作成/更新日時、削除フラグ、移行元識別子/指紋 |
| personal_event_changes | トリガーで追加する変更スナップショット。単調増加seqで差分同期（1回500件） |
| personal_event_operations | ユーザー別operationIdと結果。応答消失後の再送を二重適用しない |
| personal_sync_users | アカウントの正本切替済みフラグ。既存ミラーの個人予定は残すが参照・上書き対象から外す |

GET `/api/personal/events`（本人の現在の一覧） / GET `/api/personal/events/sync?cursor=N`（本人の差分）。

POST `/api/personal/events/create` / `update` / `delete` / `import` / `activate`。

全APIは既存Cookie認証。user_idはCookieからのみ決定。変更には許可OriginとJSON必須。update/deleteはversion一致時だけ実行、古い更新は409。削除はtombstoneで保持する。既存日付+時刻形式を維持し、端末の時計は競合判断に使わない。

## 移行・オフライン・競合

1. 初回起動時、ユーザー別キーに元の予定と元のstate文字列を変更しないバックアップとして保存。保存失敗・形式異常時は同期を開始せず、元データを残す。「移行前バックアップを保存」でJSONを外部保存可能。
2. 全予定の移行マニフェストを永続化してから1件ずつimport。D1は「認証ユーザー＋元ID＋正規化した全予定情報のSHA-256」で冪等化。元IDも内容も同一の再送のみ統合。同じIDで異なる内容は両方保存し通知する。異なるIDはタイトル・日時が同一でも勝手に統合しない。IDなしの予定も捨てず、端末の移行マニフェストで識別する。
3. アップロードとクラウド取得が成功してからactivate。移行済みレコード・削除済みレコードは古い元データの再送でも新規復活しない。元の移行バックアップと旧legacy保存キーは削除しない。旧データ引継ぎも追加バックアップを保存して同じ移行経路を使用。
4. キャッシュ・未送信操作・依存操作・seqをユーザー別localStorageに保存。起動、カレンダー再表示、フォーカス、オンライン復帰、編集時と表示中60秒間隔で差分取得。バックグラウンド常時接続は行わない。
5. 通信中または応答不明の操作は内容を変更せず再送。その後の編集は別operationIdで依存関係を保持。古い応答で取得済みの新しいversion/tombstoneを上書きしない。
6. 競合時は端末の変更とサーバーの内容を保管し、ユーザーがサーバー採用・別予定として保存・最新内容を確認して削除から選ぶ。自動で片方を破棄しない。通信失敗中も起動済み画面では予定を閲覧・編集可能。認証秘密情報は保存しない。

## 共有のプライバシー

- 正本切替済みユーザーの個人予定はD1から直接グループ一覧・空き時間計算へ反映。旧個人ミラーは残すが二重参照しない。新旧端末からのミラー更新で個人予定の正本を書き換えない。
- 他人の個人予定/シフト、別グループの正式予定はAPIで時間帯・終日・「予定あり」のみ返す。タイトル、メモ、勤務先、給与、実予定ID、所有者ID、extraなどは含めない。自分の予定と所属グループの正式予定は従来どおり。支出は共有しない。
- 非公開時間帯も空き時間計算に含む。グループの閲覧はメンバー認証必須。

## ロールバック / 復元

- まず書込みを止めて端末バックアップ・未送信queue・D1の新規/更新データを保全し、互換hotfixを優先する。Worker/frontendを以前の版に戻す場合も新テーブル、変更履歴、tombstone、各端末のバックアップを削除しない。
- 旧frontendへ戻すだけでは新D1正本を取得できず、古い端末データの再投稿があり得る。旧版をそのまま通常運用せず、読み取り/保全中心にして再公開前にD1と端末の差分を照合する。
- 通常の再移行は既存ID/指紋を維持して冪等import。本人が明示的に削除した予定を復元する場合だけバックアップから別の新IDとして登録する。tombstoneを消して自動復活させない。
- D1の全体復元/Time Travelは他機能や公開後の変更も巻き戻すため最終手段。新規データを先にエクスポートし、本人の追加承認を得てから実施する。DROP/down migrationやlocalStorage初期化はしない。

## 残る課題

- シフト・家計簿の端末間同期は今回の対象外。
- 旧端末/旧URLを一度も開かないまま、そのlocalStorageをサーバーから取得することはできない。
- PWAの完全オフライン起動は既存SWがアセットキャッシュを持たず/auth/me確認も必要なため未対応。今回のオフライン閲覧・編集は認証済みで起動済みの画面について保証。
- 同一端末で同じユーザーの複数タブを同時に編集するための跨タブ排他は未実装。端末ごとの独立キャッシュ間の同期は確認済み。複数タブの同時編集は避ける。
- 変更履歴・操作台帳・削除記録はデータ保全のため期限なしで保持。長期運用時には安全な履歴圧縮/容量監視が必要。定期同期頻度は実利用の無料枠消費を見て調整する。
- 正式な共有予定・シフトミラーの既存Push通知は維持。個人予定の新しい正本APIからの更新通知は未追加で、従来の個人ミラー更新通知経路には流れない。必要なら非公開情報を含まない専用通知を別途追加する。
